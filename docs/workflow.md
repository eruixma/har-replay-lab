# 工作原理与踩坑记录

这份文档解释「为什么这么做」，以及我们真实踩过的坑。工具本身的用法看 README。

---

## 1. 为什么 HAR 能还原一个前端

浏览器加载一个页面时，服务端返回的**就是源码**：HTML、CSS、JS 的原始字节。
HAR 记录的是这些请求的响应体（勾了 "with content" 的话），所以它其实是一份
「这个页面运行所需的全部静态资源 + 当时的接口数据」的快照。

把它按 URL 路径铺开成目录，就是一个能静态托管的站点：

```
https://example.com/assets/index-abc.js
        ↓ to-site.mjs
site/assets/index-abc.js
```

接口那部分单独拎出来做 mock，前端就会以为自己连着一个正常工作的后端。

**拿不到的是后端逻辑。** 你只拿到了输入和输出，没拿到中间怎么算的。

---

## 2. 先看三个信号，再决定值不值得做

`to-site.mjs` 的输出里有三行决定后续投入：

### `HTML: N 个`

- `N ≥ 1` → 可以继续
- `N = 0` → **别往下做了**。没有 HTML 就没有外壳，跑起来只能是空白页。
  原因几乎总是导出时 Network 过滤器停在 `Fetch/XHR`。

### `source map`

- 有且已抓到 → 恭喜，Chrome 的 Sources 面板会直接显示出 `webpack://` 原始文件树，
  变量名、目录结构、注释都是真的。这时候你是真的在读源码。
- 没有 → 只能格式化后按字符串定位（文案、`useState`、图表库名）。
  能看懂数据流和页面结构，读不到组织方式。

### `接口 N 个`

决定 mock 的规模。如果只有两三个，手工补都行；如果是几十个，就必须靠
`to-fixtures` 自动转换 + `walk.mjs` 自动找缺口。

## 3. 这类前端是「状态机」，服务端是唯一真相

现代 SPA 的典型写法：

```
用户点按钮 → 发请求 → 服务端返回【整个新状态】 → 前端整块重渲染
```

注意返回的是**整个状态**，不只是增量。所以：

- 你填什么、选哪个选项，前端不做判断，只是发出去
- 显示什么，完全由服务端返回决定
- 因此「随便点哪个按钮都能推进」是成立的（只要它们打同一个端点）

这也解释了那条铁律：**不能拼接不同会话的响应**。拼出来的状态在时序上是不存在的，
前端会渲染出一个谁也不认识的中途状态，然后后续请求全部对不上。

## 4. 流式响应：三个必须原样保留的地方

### 4.1 NDJSON 不能美化

`application/x-ndjson` 是「一行一个 JSON」。客户端逐行解析。

如果你 `JSON.parse` 再 `stringify(obj, null, 2)`，一行变成几百行，
客户端下一行就拿到 `{`，直接报：

```
Unexpected non-whitespace character after JSON at position 135 (line 2 column 1)
```

`position 135` 就是第一个对象结束的位置。见到这个报错，先查内容是不是被格式化了。

### 4.2 base64 要先解码

DevTools 的 `Network.getResponseBody` 对非 `text/*` 的 MIME 会返回
`base64Encoded: true`。`application/x-ndjson` 正好落在这个范围里。

不处理的话，前端收到的是 `eyJwcm9ncmVzcyI6...` 这种 base64 串，
报错信息会非常迷惑（"Unexpected token 'e'"）。

### 4.3 content-type 要保留

mock 服务默认按扩展名给 `application/json`。流式接口必须按原始 MIME 返回
`application/x-ndjson`，否则前端会走 `response.json()` 而不是流式解析。

所以 `_routes.json` 里每个端点都记了 `mimeType`，`serve.mjs` 按它返回。

## 5. 匹配策略：三级降级 + 序列

真实应用的路由里混着动态段：

```
/api/sessions/p1a2b3c4d5e6f7a8b/answer
```

会话 id 每次都不一样，但录制时是固定的。所以匹配按三级降级：

1. **精确**：路径完全一致
2. **归一化**：把 `p` + 十六进制、UUID、长数字这类段落换成 `:id` 再比
3. **末两段**：只比最后两段（跨会话兜底）

请求体不参与匹配。这样「换个选项 / 换个提问」都能命中同一份录制。

**同一端点多次调用**（多轮问答的典型形态）按录制顺序存成 `__1 __2 __3`，
每次请求取下一个，用完后停在最后一个。这样重放才能真实走完多步流程。

新会话（`POST /sessions` 之类）会把游标归零——下次重新开始还能从头播。

## 6. 认证：为什么总是卡在登录页

录制时你通常**已经登录了**，所以 HAR 里根本没有登录请求。
本地一跑，前端启动时发的第一个请求（常见是 `POST /api/auth/refresh`）404，
于是清空登录状态、跳 `/login`。

两种处理：

1. **自动派生**：`to-fixtures` 发现没有 `/api/auth/login` 时，用 `/auth/refresh` 的响应
   造一份。两者通常是同一个形状（`{access_token, user, ...}`）。
2. **手动补**：在原站登录一次，单独录那条请求。

顺带一个细节：如果 token 是 JWT，`exp` 会过期。`to-fixtures` 会把 `exp` 顺延 30 天，
签名保持原样——本地 mock 不校验签名，客户端只读 `exp` 判断过期。

## 7. 什么时候该放弃重放

重放适合「看流程」，不适合「造产品」。出现下面这些情况，性价比就很低了：

- **分支太多**：每个选项都是独立后端逻辑，录不过来
- **强依赖后端计算**：结果不是录制时那份就对不上（比如"根据你的数据算"）
- **实时协作/推送**：WebSocket 的长连接状态没法重放
- **鉴权复杂**：token 短命、多因素、设备指纹

判断标准很简单：**你想看的，是"长什么样"，还是"怎么算的"？**
前者重放够用，后者只能自己实现。

## 8. 我们踩过的坑（按出现顺序）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | 导出时过滤器停在 Fetch/XHR | HAR 里 19 条全是接口，没有 HTML | 过滤器改 All 重新导出 |
| 2 | 把 NDJSON 当 JSON 发 | `Unexpected non-whitespace character at position 135` | 保留原始 MIME，不美化 |
| 3 | fixtures 被 prettier 化 | 2 行变 348 行，客户端逐行解析全崩 | 流式响应原样保留 |
| 4 | 用旧会话的响应补缺口 | 界面突然变成另一个问题，后续全 404 | 别拼会话，回原站补录 |
| 5 | 选项按钮匹配不到 | 一直点空输入的 Send，毫无反应 | 按钮 textContent 带描述，用前缀匹配不要加 `$` |
| 6 | 图表明明有却判定没出图 | canvas=0 | 那是 Plotly，用 `.js-plotly-plot` 和「大尺寸 svg」判定 |
| 7 | 多轮 `/answer` 只留最后一份 | 问答原地打转 | 按序存 `__1 __2 __3` |
| 8 | 缺 login fixture | 卡在登录页 | 从 refresh 派生 |
| 9 | CDP 超时 timer 用了 unref | 进程莫名退出，报 unsettled top-level await | timer 要 ref，resolve 时 clearTimeout |

这九条基本覆盖了新用户会遇到的 90% 问题。
